# Compiler test fixtures

Knapshots keeps small test-only compiler plugins and KSP processors in its own repository, following the role that [MacroTesting's example macros](https://github.com/pointfreeco/swift-macro-testing/tree/main/Tests/MacroTestingTests/MacroExamples) play in testing MacroTesting. They are not public plugins or dependencies for library consumers.

The compiler fixture includes `@AddMember` and `@AddProperty`: annotated Kotlin classes gain a function or property. It also reports source-located `@Reject` errors and `@Caution` warnings and performs a simple IR string transformation. The plugin can write concise observations gathered in FIR and IR; those observations are intentionally small and are not full compiler dumps.

The fixture is exercised by both embedded and Gradle compiler hosts. Tests check generated functions and properties, nested and generic classes, plugin-free downstream use, failures without the plugin or annotation, type errors, multiple source-located plugin diagnostics, compiler flags, multiple source files, FIR/IR snapshots, version-specific expectations, inline recording, and transformed bytecode. A separate test-only KSP processor supplies `@AddGreeting`: it generates a greeting object for each annotated class, reports errors for invalid targets, and optionally emits a warning. KSP integration tests run the processor in an isolated Gradle project, compare and record generated source, inspect diagnostics, execute generated code, and cover multiple files, compiled dependencies, processor rounds, and multiple processors. Lightweight editor tests use the same test compiler plugin to check generated Kotlin references and plugin diagnostics; they also test ordinary Kotlin and Java editor observations. The optional KPaths integration remains useful as a cross-project test of an independent plugin; it is not required to run these tests.

The recording tests also cover nested and qualified calls, preserving neighboring comments, compiled round trips for Unicode, dollar signs, backslashes, triple quotes, and carriage returns, CRLF source files, and atomic failure of a batch. Real fixture tests cover private generated declarations, diagnostics from multiple files, and KSP warnings and errors alongside partial generated output. The recording-mode tests follow the cases in [SnapshotTesting's recording tests](https://github.com/pointfreeco/swift-snapshot-testing/blob/main/Tests/SnapshotTestingTests/RecordTests.swift): missing snapshots, existing matches and mismatches, failed-only updates, forced updates, and no-record behavior. Compiler, KSP, and editor assertions exercise these modes with inline snapshots. The fixture also tests generated output alongside diagnostics, inspired by [MacroTesting's diagnostic and expansion examples](https://github.com/pointfreeco/swift-macro-testing/blob/main/Tests/MacroTestingTests/AddBlockerTests.swift). Kotlin source ranges and IDE quick fixes remain distinct areas of work.

## Coverage to expand

[CompilationTesting's beta preview](https://www.pointfree.co/blog/posts/234-beta-preview-compilationtesting) also motivates testing source-level compiler guarantees and recording diagnostics. The fixture and assertion APIs do not yet cover every behavior from MacroTesting or CompilationTesting. In particular, future work includes:

- More declaration shapes and visibility cases beyond the generated functions and properties, nested and generic classes, and downstream JVM consumer already covered.
- Multiline diagnostic source ranges. The embedded compiler host captures optional end positions and renders same-line ranges; multiline ranges currently fall back to a start caret.
- Generated KSP resources. A disabled acceptance test demonstrates that the processor can produce a resource, but the Gradle host currently collects only Kotlin and Java sources.
- Editor diagnostics support source-annotated inline recording through an isolated worker, but version-specific editor expectations are not implemented. The worker keeps the embedded compiler off the IDE classpath to avoid conflicts with the IDE Kotlin plugin.
- Diagnostic notes and fix-it or IDE quick-fix assertions where Kotlin's APIs expose them. Kotlin compiler diagnostics and IDE quick fixes are different APIs, so Swift fix-it behavior should not be assumed to map directly.
- Additional source formatting and escaped-string recording cases, language-mode options, and scenarios where a test should unexpectedly succeed or fail.
- Further Kotlin-specific boundaries such as compiler-plugin ordering, bytecode bridges, and full imported-project IDE resolution. KSP multi-round and multiple-processor cases and lightweight IDE resolution are covered; they do not replace full IDE integration.

Keep fixture behavior small and deterministic. Add an example for a distinct testing capability rather than reproducing a production library's feature set.

## Next coverage pass

After adopting the input-first assertions in KPaths, extend the fixture tests with small, independently meaningful scenarios. Keep bytecode capture explicit and preserve tests of existing snapshots across all recording modes.

1. **Source rewriting and recording:** Extend the existing multiple-assertion, concurrent, stale-source, qualified/nested, escaped-string, line-ending, and failed-batch tests with additional supported Kotlin call shapes and end-to-end replay scenarios. Verify that unsuccessful rewrites leave the file untouched and that recordings compile and pass on the next run. Test `missing`, `failed`, `all`, and `none` with missing, matching, and changed expectations across compiler, KSP, and editor assertions.
2. **Diagnostics:** Add real compiler and processor cases with multiple errors and warnings, different files, tabs and Unicode, missing locations, and diagnostics emitted together with generated output. Check unexpected diagnostics and outcome-only assertions separately. Expand range tests across compiler versions and multiline source; never invent a range when the host does not report one. The embedded host retains optional start and end positions from `MessageCollector` and renders valid single-line ranges. Its callback supplies severity, rendered message, and location rather than a structured parent/child diagnostic or fix-it contract. The Gradle host currently reports build output as one failure diagnostic.
3. **Compiler and KSP behavior:** Test visibility, nested and generic declaration shapes, conflicting names, language options, plugin ordering, multiple source files, compiler failures before and after generation, and plugin-free downstream use. Include multiple KSP rounds and processors, with generated source and diagnostics together. Keep generated resources as a separately tracked feature: the current KSP host collects source files only.
4. **Editor assertions:** Cover exact diagnostic locations, multiple files, references that resolve and fail to resolve, and warning/error changes using both the lightweight fixture and an imported project. Add version-specific editor snapshots when supported, then verify that the right expectation is selected for the IDE/compiler combination. Test both KEFS and standalone IDE-plugin integrations when available; a lightweight fixture is not a substitute for an imported project.
5. **Cross-project and compatibility:** Run the same real KPaths assertions against the current Knapshots build, test at least two supported Kotlin compiler versions, and run representative editor scenarios in the existing IDE matrix. Exercise a downstream consumer that does not apply the compiler plugin, and validate a separately resolved artifact once publication is available.

### Diagnostic ranges, notes, and fixes

A range identifies the beginning and end of the affected source, allowing a snapshot to underline the full expression instead of just placing a caret. Kotlin 2.4.21's `CompilerMessageSourceLocation` exposes `lineEnd` and `columnEnd` (whose default implementations return `-1`). A real unresolved-reference test confirms an exclusive end column for that diagnostic. Same-line ranges are rendered; missing, invalid, or multiline ranges fall back to a caret. MacroTesting also skips multiline highlights when drawing underlines in its plain-text diagnostic snapshots; see its [underline implementation](https://github.com/pointfreeco/swift-macro-testing/blob/main/Sources/MacroTesting/Internal/Diagnostic%2BUnderlineHighlights.swift). Availability across compiler versions and KSP and IDE observations need separate verification.

A note is related context, such as the location of a conflicting declaration. The embedded CLI callback does not itself describe parent/child relationships, and the current host ignores messages other than errors and warnings. Investigate whether particular compiler APIs expose structured related information before associating messages; otherwise retain unstructured messages without pretending they are linked.

A fix changes source, such as replacing an invalid expression. IntelliJ provides intention/quick-fix testing through `findSingleIntention()` and `launchAction()`; a Knapshots editor assertion could locate an action, apply it, and compare the resulting source. See [JetBrains' test documentation](https://plugins.jetbrains.com/docs/intellij/writing-tests.html) and [intention preview documentation](https://plugins.jetbrains.com/docs/intellij/code-intentions-preview.html). This is an IDE capability and should not be presented as a universal CLI compiler fix-it API. Multi-file edits, unavailable fixes, and action side effects need explicit tests.
